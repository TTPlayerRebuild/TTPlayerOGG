# OGG 真实 HTTP 边界与 Opus 定位验证

日期：2026-10-25。补充 [上一轮 IStream 故障注入](STREAM_BOUNDARIES_20261024.md) 的真实 HTTP 验证。本轮未修改 OGG 生产代码，保留已发行 `2026.10.24p1` DLL。

## 实际测试链路

测试程序直接编译当前 `rebuild/src/audio/http_stream.cpp`，加载当前 `ttp_https.dll` 流接口和实际 `ttp_ogg.dll`，连接本机临时 HTTP 服务。XP／Win7 通过 VirtualBox NAT 访问同一服务；没有用内存 IStream 代替网络传输。

两种编码分别使用 12 秒 Vorbis 6 声道和 Opus 立体声文件。每种编码验证十条路径：

| 路径 | 验收条件 |
| --- | --- |
| 普通 200 响应、忽略 Range | 完整 PCM 与本地基线逐字节相同；定位成功 |
| 首次 200、后续 Range 206 | 同上 |
| 206 分段读取 | 同上 |
| chunked、未知长度 | 完整 PCM 正确；不声明定位能力，Seek 返回 E_NOTIMPL |
| 首次响应中途断开，ETag 不变且可续传 | 完整 PCM 正确，无重复或丢失 |
| 中途断开且无法安全续传 | 返回错误，不伪装为正常 EOF |
| 续传 ETag 改变 | 拒绝拼接两个不同资源 |
| 读取等待期间取消 | 返回 ERROR_CANCELLED；测试的 200 ms 取消在 1,500 ms 限额内完成 |
| 响应停滞 | 返回超时错误，不报告正常 EOF |

timeout 配置为 1,000 ms，允许 HttpStream 的续传尝试，因此总耗时可能超过单次 timeout。服务器按请求前缀隔离 XP、Win7 的故障计数，并记录实际 Range 请求；测试结束后关闭服务。

## Opus 的定位位置与解码历史

首次测试将 Opus 定位后的 PCM 与从头连续解码的同一区间直接比较，发现开头短区间不逐位相同。这不能直接判为网络或插件错误。

另写独立探针，直接静态链接相同版本的上游 libopusfile／libopus／libogg，从本地文件调用 `op_pcm_seek`，完全绕过本插件和 HttpStream。定位到 6,000 ms 后：

- 实际帧数正确，剩余 288,000 帧；
- HTTP 普通、Range、续传路径的尾部均与这个独立上游输出逐字节相同；
- 独立上游与连续解码同样存在短暂的状态收敛差异：本样本最大绝对差约 0.003753、RMS 约 0.000142，最后一个不同值位于定位后约 459 ms；这些数值仅描述本样本。

[RFC 7845 §4.6](https://www.rfc-editor.org/rfc/rfc7845.html#section-4.6) 要求定位时至少预滚 80 ms，帮助恢复解码状态；它不要求预滚后所有浮点值与从头解码逐位相同。[上游对预滚的讨论](https://github.com/xiph/opus/issues/96) 也区分了这两个目标。因此本次用直接上游定位作为独立 PCM 参考，并保持插件的正常定位效率，没有改成每次从文件开头解码。

## 尚未覆盖

本次为真实 HTTP 传输与核心接口验收，不等同于播放器网络界面、公共服务器或 TLS 证书链验收。仍需单独验证实际超大流、实时无限流、每次读取返回 E_PENDING 的异步调用约定，以及不同服务器／代理的协议变体。未知长度的成功顺序播放不能解释为支持任意位置跳转。
